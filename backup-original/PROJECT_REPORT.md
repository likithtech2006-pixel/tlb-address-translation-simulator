## 1. Problem Statement

A CPU generates virtual addresses, while physical memory is accessed through physical addresses. In a paging-based memory system, a virtual address is divided into a virtual page number and a page offset. The page table maps a virtual page to a physical frame. Looking up the page table for every memory reference can add overhead. A Translation Lookaside Buffer (TLB) is a small, fast associative cache that stores recently used page-to-frame mappings and can accelerate address translation when the requested page is present.

The problem addressed by this project is to make the TLB translation process understandable and observable. A student should be able to enter virtual addresses, inspect page-number and offset calculations, observe TLB hits and misses, follow page-table lookup on a miss, see valid mappings inserted into the TLB, understand replacement when the TLB is full, and inspect the resulting physical address and performance statistics. Invalid page-table entries should be reported as page faults rather than being assigned invented physical addresses.

This project implements an interactive browser-based model of TLB-based virtual-to-physical address translation. Users can configure address widths, page size, TLB capacity, initial mappings, and replacement policy; run single addresses, sequences, random workloads, or a presentation demo; and inspect the TLB, page table, physical frames, history, hit/miss statistics, and simplified effective access time (EAT).

## 3. Introduction

Virtual memory gives a process a virtual address space. Paging divides the virtual address space into fixed-size pages and physical memory into frames of the same size. The operating system maintains a page table that records which physical frame corresponds to each valid virtual page. Because pages and frames have equal sizes, the offset within the page is unchanged during translation.

The TLB is a small associative cache of recent page-table mappings. If a requested virtual page is found in the TLB, the translation is a **TLB hit**. If it is absent, the system has a **TLB miss** and consults the page table. A valid page-table mapping supplies the frame number, and the mapping may be inserted into the TLB. If the page-table entry is invalid, the simulator reports a page fault. Actual operating systems may then load a page or terminate a process; servicing that fault is outside this simulator's model.

## 4. Operating System Concept: TLB

### 4.1 Virtual address, page, frame, and offset

A virtual address is the address generated by the CPU. For page size `S`:

- `page number = floor(VA / S)`
- `offset = VA mod S`
- `physical address = frame number × S + offset`, if the page is mapped

For a page size of `2^n` bytes, the offset uses `n` bits. The remaining virtual-address bits represent the virtual page number.

### 4.2 TLB hit

A TLB hit occurs when the requested page number is present in a valid TLB entry. The simulator takes the cached frame number and combines it with the original offset. No page-table lookup is counted for a hit.

### 4.3 TLB miss

A TLB miss occurs when the page number is not in the TLB. The simulator checks the page table and increments the page-table lookup counter. If the entry is valid, it obtains the frame number, inserts the page-to-frame mapping into the TLB, and calculates the physical address. If the TLB is full, the selected replacement policy chooses an entry to evict.

### 4.4 Page fault model

If the page-table entry is invalid, the simulator reports `PAGE FAULT`. No frame or physical address is generated and no successful data-memory access is counted. This is a simplified teaching model; it does not emulate backing-store I/O or fault handling.

### 4.5 Replacement policies

- **FIFO (First In, First Out):** Evict the TLB entry with the earliest insertion timestamp.
- **LRU (Least Recently Used):** Evict the entry with the oldest last-access timestamp.

## 8. Algorithm

1. Read the configuration and initialize page-table entries, physical frames, empty TLB, counters, and history.
2. Read a virtual address `VA` and reject it if it is not an integer in `[0, 2^virtualBits − 1]`.
3. Compute `page = floor(VA / pageSize)` and `offset = VA mod pageSize`.
4. Search the TLB for a valid entry whose page number equals `page`.
5. If found, count a hit, update its last-access timestamp, and use the cached frame number.
6. Otherwise, count a miss and a page-table lookup.
7. If the page-table entry is invalid, count a page fault, store a history record without a frame or physical address, and stop this translation.
8. If the page-table entry is valid, obtain its frame number. If the TLB is full, select the FIFO or LRU victim and remove it. Insert the new page/frame mapping.
9. Calculate `PA = frame × pageSize + offset` and count a successful memory access.
10. Update the live view, counters, ratios, history, and explanation panel.

## 9. Pseudocode

```text
TRANSLATE(VA):
    if VA is not an integer or VA < 0 or VA >= 2^virtualBits:
        report input error
        return

    page   = floor(VA / pageSize)
    offset = VA mod pageSize
    entry  = TLB.find(page)
    totalTranslations += 1

    if entry exists and entry.valid:
        tlbHits += 1
        update entry.lastAccess
        frame = entry.frame
    else:
        tlbMisses += 1
        pageTableLookups += 1
        pte = pageTable[page]

        if pte.valid == false:
            pageFaults += 1
            record VA, page, offset, PAGE FAULT, no frame, no PA
            return

        frame = pte.frame
        if TLB is full:
            if policy == FIFO:
                victim = entry with earliest insertion timestamp
            else if policy == LRU:
                victim = entry with oldest last-access timestamp
            remove victim
        TLB.insert(page, frame, valid=1)

    PA = frame * pageSize + offset
    memoryAccesses += 1
    record VA, page, offset, hit/miss, frame, PA
    update statistics and interface
```

## 10. Implementation Details

The project is built with standard HTML, CSS, and JavaScript and runs in the browser. No build process or external JavaScript dependency is required.

- `index.html` contains the dashboard, controls, visualization panels, tables, learning content, and project information.
- `styles.css` defines the light-first theme, dark mode, responsive breakpoints, card/table styling, hover states, translation highlights, and print styles.
- `simulator.js` contains configuration validation, address arithmetic, TLB and page-table state, FIFO/LRU eviction, statistics, workload modes, history, CSV export, and EAT calculation.

### Configuration and mapping model

The default model uses 16-bit virtual addresses, 12-bit physical addresses, 256-byte pages, four TLB entries, LRU replacement, and sequential initial mappings. The first `number of physical frames` virtual pages are mapped one-to-one to frames; remaining pages are invalid. Users can choose sparse or empty mappings for demonstrations.

### Workload modes

- Single address: translates the value entered by the user.
- Address sequence: processes comma-, semicolon-, or whitespace-separated addresses in order.
- Random: generates 12 valid virtual addresses for the current virtual-address width.
- Step-by-step: reveals the CPU request, address split, TLB lookup, page-table lookup when required, and physical address or page fault.
- Demo mode: automatically runs a short workload that demonstrates repeat access, a miss, an invalid page when one exists, and changing statistics. Speed is configurable.

### Statistics definitions

- `Hit ratio = TLB hits / total translations`
- `Miss ratio = TLB misses / total translations`
- `Page-table lookups`: incremented for every TLB miss, including one that finds an invalid page-table entry.
- `Page faults`: invalid page-table entries encountered.
- `Memory accesses`: successful translations that reach the data-memory access stage; page faults do not increment this count.

### Effective Access Time (EAT)

The calculator uses a simplified one-level page-table model:

- Hit cost: `t + m`
- Miss cost: `t + 2m`
- `EAT = h(t + m) + (1 − h)(t + 2m)`

Here `t` is TLB lookup time, `m` is one memory access time, and `h` is the hit ratio from 0 to 1. Page-fault service time is excluded. This is an explicit teaching assumption; other textbook models may use different assumptions about whether the TLB lookup overlaps with memory access.

### Invariant checks

For every successful translation:

- `0 ≤ offset < pageSize`
- `page = floor(VA / pageSize)`
- `offset = VA mod pageSize`
- `PA = frame × pageSize + offset`
- `0 ≤ PA < 2^physicalBits`
- `hits + misses = total translations`
- `page-table lookups = TLB misses` in this model
- `successful memory accesses = total translations − page faults`

## 15. Limitations

- This is a teaching simulator, not a hardware TLB or operating-system kernel implementation.
- It models a simplified single-level page table and does not emulate multi-level page tables, ASIDs, permissions, dirty bits, page-table walks across multiple levels, or concurrent processes.
- Page faults are detected but not serviced; there is no backing-store simulation or replacement of pages in physical RAM.
- Initial mappings are predetermined by the selected mapping mode rather than dynamically loaded into frames.
- The EAT formula excludes page-fault service time and assumes one page-table memory access on a miss.
- The page-table and physical-memory visualizations cap the number of rendered rows/frames for responsiveness in large configurations.
- Translation history and theme preferences are local to the current browser session/device; no cloud persistence is implemented.

## 20. Viva Questions and Answers

**Q1. What is a TLB?**  
A TLB is a small, fast associative cache that stores recently used virtual-page-to-physical-frame mappings.

**Q2. Why is a TLB needed?**  
It reduces the average address-translation overhead by avoiding a page-table lookup for a TLB hit.

**Q3. What is a TLB hit?**  
The requested virtual page is found in a valid TLB entry, so its frame number can be used directly.

**Q4. What is a TLB miss?**  
The requested page is not in the TLB. The system must consult the page table to determine whether a valid mapping exists.

**Q5. Does a TLB miss always mean a page fault?**  
No. A TLB miss means only that the mapping is not cached. If the page-table entry is valid, the mapping is retrieved and cached. A page fault occurs in this simulator when the page-table entry is invalid.

**Q6. What is the page offset?**  
It identifies the byte within a page. Since a page and frame have the same size, the offset is preserved during translation.

**Q7. How is the physical address calculated?**  
`PA = frame number × page size + offset`.

**Q8. Why must page size be a power of two for the bit-splitting model?**  
A power-of-two page size lets the offset be represented by a fixed number of low-order bits, equal to `log2(page size)`.

**Q9. What is the difference between FIFO and LRU?**  
FIFO evicts the entry inserted earliest; LRU evicts the entry that has not been accessed for the longest time.

**Q10. What happens when a valid mapping is found after a TLB miss?**  
The frame number is obtained from the page table, the mapping is inserted into the TLB, and the physical address is calculated.

**Q11. What happens if a page-table entry is invalid?**  
The simulator reports a page fault and does not produce a physical address. Real OS fault handling is outside the project scope.

**Q12. What does the hit ratio mean?**  
It is the number of TLB hits divided by total address translations, usually expressed as a percentage.

**Q13. What is effective access time?**  
EAT is the expected average time for the modeled translation and memory-access path, weighted by the hit ratio and miss ratio.

**Q14. What EAT model does this project use?**  
Hit cost is `t + m`; miss cost is `t + 2m`; therefore `EAT = h(t + m) + (1 − h)(t + 2m)`. It excludes page-fault service time.

**Q15. Why does the offset not change?**  
Paging changes the page number into a frame number, but the byte's position within the fixed-size page/frame stays the same.

**Q16. Is this an actual hardware TLB?**  
No. It is a software model for learning the algorithm and visualizing its behavior.

**Q17. What is the role of the valid bit?**  
It indicates whether an entry contains a usable mapping. An invalid page-table entry cannot supply a frame number in this model.

**Q18. Why can a TLB replacement occur?**  
The TLB has a limited number of entries. When it is full and a new valid mapping must be inserted, an existing entry must be evicted according to the configured policy.

**Q19. What is the difference between virtual pages and physical frames?**  
Pages divide the virtual address space; frames divide physical memory. Both have the same size, and the page table maps valid virtual pages to frames.

**Q20. What are the main limitations of the simulator?**  
It models one-level paging and TLB behavior only. It does not implement real hardware, disk-backed page-fault service, multi-level page tables, process isolation, or OS kernel integration.
